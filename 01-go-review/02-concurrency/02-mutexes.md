# М'ютекси (sync.Mutex / sync.RWMutex)

> Пакет `sync`. Захищають спільний стан від одночасного доступу горутин.

---

## Навіщо потрібен

Go виконує горутини справді паралельно на багатьох ядрах (на відміну від Node.js з його одним потоком). Коли кілька горутин одночасно читають/пишуть одну змінну, виникає **data race** — гонка даних.

```go
var counter int
var wg sync.WaitGroup

func main() {
    for i := 0; i < 1000; i++ {
        wg.Go(func() {
            counter++   // ГОНКА!
        })
    }
    wg.Wait()
    fmt.Println(counter) // 847, 992, 1000... — непередбачувано
}
```

Чому ламається: `counter++` — це НЕ одна операція, а три кроки:
1. прочитати значення з пам'яті
2. додати 1
3. записати назад

Дві горутини можуть прочитати одне й те саме число (напр. 500), обидві додати 1, обидві записати 501. Одна інкрементація втратилась.

> **Аналогія з JS/Node:** Node однопотоковий, тому `counter++` там безпечний «даром». У Go істинна паралельність — без замка дані тихо псуються. Це головна різниця менталітету при переході з JS.

**Гонку НЕ видно в обычному запуску.** Її ловить лише race-детектор:
```bash
go run -race main.go
# WARNING: DATA RACE
# Write at 0x... by goroutine 7:
#   main.main.func1()
```

## Базове використання

```go
var (
    mu      sync.Mutex
    counter int
)

func inc() {
    mu.Lock()           // захопити замок (якщо хтось тримає — чекай)
    defer mu.Unlock()   // відпустити при будь-якому виході з функції
    counter++
}
```

Тільки одна горутина може бути між `Lock()` і `Unlock()`. Решта блокуються на `Lock()` і чекають своєї черги.

### `defer mu.Unlock()` — обов'язковий ідіом

`defer` гарантує, що замок зніметься навіть якщо далі буде `return`, `panic` або помилка:
```go
func update() (err error) {
    mu.Lock()
    defer mu.Unlock()   // спрацює при будь-якому виході
    // ... робота, що може впass/panic ...
    return
}
```
Забудеш `Unlock()` у якійсь гілці → усі інші горутини зависнуть назавжди (**дедлок**).

## `sync.RWMutex` — багато читачів, мало писарів

Звичайний `Mutex` ексклюзивний навіть для читання. `RWMutex` має два режими:

| Метод | Хто | Правило |
|-------|-----|---------|
| `RLock()` / `RUnlock()` | читачі | можуть читати **одночасно** |
| `Lock()` / `Unlock()` | писар | ексклюзивно; чекає, поки всі читачі вийдуть |

```go
var (
    mu   sync.RWMutex
    data = map[string]int{}
)

func Get(k string) int {
    mu.RLock()              // спільне читання — багато горутин паралельно
    defer mu.RUnlock()
    return data[k]
}

func Set(k string, v int) {
    mu.Lock()              // ексклюзивний запис — читачі чекають
    defer mu.Unlock()
    data[k] = v
}
```

Виграш відчутний, коли читання в 10–100 разів частіше за запис (кеш, конфіг, route-таблиця). Якщо запис/читання приблизно рівні — бери звичайний `Mutex`, він швидший (менше накладних витрат).

## Типові пастки

### 1. Копіювання м'ютекса
`Mutex` містить внутрішній стан. Копіювати його за значення — поламати синхронізацію. `go vet` це ловить.

```go
type Counter struct {
    mu sync.Mutex
    n  int
}

func bad() {
    c := Counter{}
    use(c)   // ПОМИЛКА: передаємо копію, замок працює на копії
}

func good() {
    c := &Counter{}  // завжди вказівник
    use(c)
}
```
Правило: якщо структура містить `Mutex` — передавай її тільки за вказівником (`*Counter`).

### 2. Вкладений Lock (нерекурсивність)
```go
mu.Lock()
mu.Lock()   // ДЕДЛОК: сам себе заблокував і чекаєш себе
```
Go-м'ютекс не рекурсивний. Якщо функція під замком викликає іншу, що теж бере той самий замок — дедлок.

### 3. Дедлок через два замки
Горутина A тримає `mu1` і чекає `mu2`; горутина B тримає `mu2` і чекає `mu1`. Обидві стоять вічно.
Розв'язок: завжди захоплюй замки в **єдиному порядку** (напр. спочатку `mu1`, потім `mu2`).

### 4. Тримати замок під час повільної операції
```go
mu.Lock()
http.Get(url)   // ПОГАНО: мережа триває секунди, усі чекають
mu.Unlock()
```
Під замком — лише швидке читання/запис поля. Мережу, диск, вивід — робімо **поза** замком, а під замком лише забираємо/кладаємо дані.

### 5. Гонка, яку м'ютекс не покриває
Якщо частина коду звертається до змінної **без** замка — гонка лишається. Правило: до спільного поля — або завжди під замком, або ніколи.

## `map` + м'ютекс vs `sync.Map`

Звичайну `map` в Go **не можна** читати/писати з кількох горутин одночасно — буде паніка `fatal error: concurrent map writes` (це не відновлюється, навіть `recover`).

Два варіанти:

### Варіант 1: `Mutex` + звичайна map (частше правильний)
```go
var (
    mu sync.RWMutex
    m  = map[string]int{}
)
mu.Lock()
m["k"] = 42
mu.Unlock()
```

### Варіант 2: `sync.Map` (спеціалізований)
```go
var m sync.Map
m.Store("k", 42)
v, ok := m.Load("k")
m.LoadOrStore("k", 100)  // атомарно: якщо нема — запише
m.Delete("k")
```
`sync.Map` оптимізований під два сценарії:
- ключі зберігаються раз і майже не змінюються (read-mostly);
- ключі належать різним підмножинам (шардинг).

У решті випадків `Mutex` + map швидший. Не бери `sync.Map` «просто так».

## М'ютекс vs Канал — коли що

| Потрібно | Інструмент |
|----------|-----------|
| Захистити **стан** (лічильник, кеш, поле) | `sync.Mutex` |
| Передати **володіння даними** між горутинами | канал |
| Організувати чергу задач / fan-out | канал |
| Атомарний лічильник без блокувань | `atomic.Int64` (sync/atomic) |

Головний принцип Go (Rob Pike):

> «Don't communicate by sharing memory; share memory by communicating.»

Тобто замість «захищати спільну змінну м'ютексом» часто краще «передати дані по каналу в одну горутину-власника». М'ютекс — коли канал надлишковий або незручний (коротка критична секція над полем структури).

## Короткий чеклист

- [ ] Спільна змінна пишеться з кількох горутин → потрібен `Mutex` або канал.
- [ ] `Unlock` завжди через `defer`, одразу після `Lock`.
- [ ] Структура з `Mutex` передається тільки за вказівником.
- [ ] Під замком — тільки швидкі операції, не мережа/диск.
- [ ] Один і той самий замок не захоплюється двічі (нерекурсивність).
- [ ] Замки захоплюються в єдиному порядку (проти дедлоку двох замків).
- [ ] Запуск |> `go run -race` |> перед комітом.

## Вправи

1. **Виправ гонку.** Візьми приклад з `counter++` (1000 горутин). Запусти з `-race` (побач гонку), потім додай `Mutex` і перевір, що результат завжди 1000.

2. **RWMutex.** Створи структуру `Cache` з `map[string]string` і методами `Get`/`Set`. Використай `RWMutex`. Напиши тест, який запускає 100 читачів і 10 писарів паралельно під `-race`.

3. **Дедлок навмисно.** Напиши код, що двічі бере `Lock()` — переконайся, що програма зависає. Потім виправ через `defer Unlock()`.

4. **sync.Map.** Перепиши приклад з вправи 2 на `sync.Map` і порівняй читабельність (а не лише швидкість).

5. **Mutex vs канал.** Реалізуй лічильник двома способами: (а) `Mutex`+`int`, (б) горутина-власник, яка приймає інкременти по каналу. Порівняй, який код тобі зрозуміліший.
